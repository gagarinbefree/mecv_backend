# MECV backend

[![Tests and build](https://github.com/gagarinbefree/mecv_backend/actions/workflows/ci.yml/badge.svg?branch=main)](https://github.com/gagarinbefree/mecv_backend/actions/workflows/ci.yml)

Backend цифровой визитки на TypeScript, NestJS, Prisma и Apollo GraphQL.

HTTP GraphQL API читает профиль из PostgreSQL через Prisma 7 и предоставляет встроенный Apollo Sandbox. NestJS собирает приложение через функциональные провайдеры без собственных классов. При запуске автоматически применяются миграции и транзакционный seed; вложенные коллекции читает DataLoader. Docker Compose запускает API вместе с отдельной PostgreSQL.

Контракт запроса profile и связанных типов описан в [GraphQL-схеме](src/profile/profile.graphql). GraphQL Code Generator создаёт из SDL типы данных и резолверов. HTTP-тесты проверяют вложенные данные, отсутствующий профиль, интроспекцию, HTML Sandbox и обработку ошибок. Скаляру Date разрешены только существующие календарные даты в формате YYYY-MM-DD, годы 0001–9999.

Плашка отражает фактический результат workflow Tests and build в GitHub Actions. Зелёный статус означает, что генерация типов, ESLint, проверка типов, тесты и сборка завершились успешно; отсутствие запусков не является подтверждением успеха.

## Локальный запуск

Нужны Node.js 24.15 или совместимый более новый patch ветки 24 и PostgreSQL. Сначала создай базы и локальные env-файлы по разделу «Локальная проверка» ниже.

~~~shell
npm ci
npm start
~~~

Перед запуском автоматически генерируются типы и выполняется сборка, включая копирование SDL в dist. Затем приложение проверяет конфигурацию и соединение PostgreSQL, выполняет `prisma migrate deploy`, заполняет демопрофиль и только после этого открывает HTTP-порт. Готовая пустая база должна существовать заранее: приложение создаёт таблицы и данные, но не кластер и не пользователя PostgreSQL.

Открой [Apollo Sandbox](http://127.0.0.1:3000/graphql). Страница загружает редактор с CDN Apollo, поэтому для редактора нужен доступ в интернет; GraphQL API работает локально. Для остановки нажми Ctrl+C. По умолчанию используются HOST=127.0.0.1 и PORT=3000. Настройки можно изменить через окружение или .env; PORT=0 назначает свободный порт, фактический URL выводится после успешного запуска.

Ошибка конфигурации, соединения, миграции, seed или открытия HTTP-порта завершает процесс с ненулевым кодом. При ошибке подготовки HTTP не открывается, пул закрывается. Повторный запуск сохраняет идентификаторы демопрофиля и не меняет другие профили. Изменения внутри управляемого демопрофиля синхронизируются с исходными демонстрационными данными при каждом старте.

Пример запроса:

~~~graphql
query {
  profile {
    name
    description
    links { label url }
    skills { name }
    experience { company position startDate endDate achievements }
    projects { name description url }
  }
}
~~~

Исходные данные в [profile-seed-data.ts](src/profile/profile-seed-data.ts) явно обозначены как учебные и используются только для заполнения БД. API читает сохранённые записи и видит изменения в PostgreSQL в следующем запросе. Профиль со slug `demo-profile` выбирает [сервис](src/profile/profile.service.ts). Отсутствие профиля возвращает null, а ошибка чтения — стандартный ответ GraphQL без стека реализации.

## Docker Compose

Нужны Docker Engine и Docker Compose v2. [Dockerfile](Dockerfile) собирает приложение на Node.js 24.15.0 Debian Bookworm, генерирует типы и удаляет dev-зависимости. Финальная стадия содержит готовый dist, production-зависимости и историю Prisma. Процесс работает от пользователя node; секреты, локальный node_modules и сгенерированные Windows-файлы исключены из контекста сборки. OpenSSL установлен для schema engine Prisma 7.

Скопируй `.env.docker.example` в `.env.docker`, замени пароль длинной строкой из латинских букв и цифр, затем выполни:

~~~shell
docker compose --project-name mecv --env-file .env.docker up --build --detach --wait
~~~

Открой [Apollo Sandbox](http://127.0.0.1:3100/graphql). [Compose](compose.yaml) создаёт собственные сеть и volume PostgreSQL 17.5; установленная на компьютере PostgreSQL не нужна. База не публикует порт на хосте. После успешного healthcheck БД приложение самостоятельно применяет миграции, выполняет seed и открывает HTTP.

По умолчанию API доступен только на loopback, порт 3100. Для доступа из локальной сети задай в `.env.docker` `MECV_BIND_ADDRESS` равным LAN-адресу сервера и при необходимости измени `MECV_HTTP_PORT`. Пароль Compose не связан с пользователем локальной PostgreSQL. Поскольку он входит в URL подключения, другие символы требуют URL-кодирования; пример использует только буквы и цифры. Не добавляй `.env.docker` в Git. Изменение пароля в env-файле не меняет пароль уже созданного PostgreSQL volume.

`GET /health` возвращает `200` и `{"status":"ok"}` без чтения профиля и кэширования. Он подтверждает работу HTTP-процесса, который начинает слушать только после подготовки БД. Проверка не является постоянной диагностикой соединения PostgreSQL. Compose использует этот маршрут без curl и дополнительных пакетов. Node.js получает SIGTERM и закрывает приложение; init-процесс освобождает завершённые дочерние процессы Prisma.

Остановка с сохранением данных:

~~~shell
docker compose --project-name mecv --env-file .env.docker down
~~~

Повтори команду `up` для запуска с прежним volume. Не добавляй `--volumes`, если данные нужно сохранить. Для проверки состояния и журналов используй `ps` и `logs backend` с теми же `--project-name` и `--env-file`.

Проверка образа и запуска с нуля:

~~~shell
npm run test:docker
~~~

Команда требует Node.js 24 и доступа к Docker. Она создаёт случайный отдельный Compose-проект, случайный пароль и новый volume, проверяет GraphQL со всеми разделами, Sandbox, healthcheck и пользователя без root. Затем удаляет контейнеры, сохраняя volume, запускает их заново и сравнивает ответ API и SQL-идентификаторы всех записей. В finally удаляются только ресурсы тестового проекта, включая его volume. Рабочий проект mecv не используется. Для Docker CLI можно задать обычные DOCKER_CONTEXT или DOCKER_HOST.

В GitHub Actions `npm test` после успешного Vitest выполняет эту же Docker-проверку; её ошибка завершает существующий workflow с ошибкой. Локально `npm test` использует обычную PostgreSQL, а Docker проверяется отдельной командой. Плашка в начале README отражает результат всего workflow.

## Архитектура чтения

[Резолверы](src/profile/profile.resolvers.ts) обращаются к типизированному контексту операции: сервис читает основные поля, а DataLoader лениво загружает только выбранные коллекции. [Предметный контракт репозитория](src/profile/profile.repository.ts) не зависит от Prisma и GraphQL. [Реализация на Prisma](src/database/create-profile-repository.ts) использует select основных полей и пакетные запросы с WHERE profileId IN (...), без универсального CRUD и разбора GraphQL AST.

У приложения один PrismaClient и пул. Их создаёт фабрика провайдера NestJS, а lifecycle закрывает соединения вместе с приложением. Сервис с мемоизацией основного профиля и четыре DataLoader создаются заново для каждой операции GraphQL. Повторные алиасы внутри операции используют общий результат; новые HTTP-запросы получают новый кэш, включая случай ранее отсутствующего профиля.

| Выборка одного профиля | Число SELECT |
| --- | --- |
| Только name и/или description | 1 |
| Основные поля и один раздел | 2 |
| Все четыре раздела | 5 |
| Повторные алиасы профиля и одного раздела | 2 |

Несколько фиксированных запросов к разным таблицам не образуют N+1. Тесты сравнивают малый пакет и двадцать настоящих профилей: каждый выбранный раздел остаётся одним SELECT. Batch-функции сохраняют порядок входных ключей, включая повторы; отсутствующие связи возвращают []. Сортировка внутри коллекций задана явно по sortOrder и id. SQL DATE преобразуются в календарные строки UTC без локального смещения.

Тесты измеряют реальные SELECT через события Prisma, проверяют выборочное чтение по HTTP, изоляцию кэша и освобождение SQL-сессий после закрытия сервера. SQL-параметры и значения подключения не выводятся.

## Локальная проверка

Нужны Node.js 24.15 или совместимый более новый patch ветки 24 и локальная PostgreSQL. Миграции и интеграционные тесты проверены на PostgreSQL 17.5 в Windows; CI использует PostgreSQL из образа ubuntu-24.04 (ветка 16).

Создай пустые базы `mecv_dev`, `mecv_test` и `mecv_shadow` под локальным пользователем PostgreSQL. Например, в psql с правом создания баз:

~~~sql
CREATE DATABASE mecv_dev;
CREATE DATABASE mecv_test;
CREATE DATABASE mecv_shadow;
~~~

Скопируй `.env.example` в `.env`, `.env.test.example` в `.env.test` и замени USER/PASSWORD локальными параметрами. Рабочие env-файлы игнорируются Git. База тестов должна быть отдельной, называться `mecv_test` и находиться на localhost; запуск на базе разработки отклоняется до подготовки схемы.

~~~shell
npm ci
npm run check
~~~

Отдельные команды: npm run lint, npm run typecheck, npm test и npm run build. Каждая автоматически обновляет типы GraphQL и Prisma Client перед запуском. Генерация и сборка не требуют работающей базы. Сборка помещает JavaScript и SDL в dist. HTTP-тесты используют свободные локальные порты и закрывают приложение после каждой проверки.

Интеграционные тесты применяют `prisma migrate deploy` к уникальной пустой схеме внутри `mecv_test`, проверяют повторный запуск миграций и ограничения базы, затем удаляют только свою схему. Проверки startup начинают без ручных миграций и seed: проверяются первый HTTP-запрос, повторный запуск, сохранность чужих данных, ошибки подготовки и отсутствие открытого порта после сбоя. Отдельные процессы запускают собранный dist/main.js из другой рабочей папки, проверяя Sandbox, параметры PORT/HOST и код завершения при ошибках. Моки Prisma не используются.

В GitHub Actions команда `npm test` автоматически запускает собственный временный кластер PostgreSQL из установленных на runner бинарников. Порт выбирается автоматически, пароль генерируется на запуск, сервер и файлы удаляются после тестов, в том числе при их падении. Docker, service containers и изменение системной службы не требуются. Ошибка подготовки базы останавливает проверку.

## Схема и миграции PostgreSQL

[Схема Prisma](prisma/schema.prisma) разделяет профиль, профессиональные ссылки, навыки, опыт и проекты. У профиля уникальный slug, у дочерних записей — стабильный key в пределах профиля. Для коллекций предусмотрены индексы `(profileId, sortOrder, id)` и детерминированная сортировка по позиции и идентификатору. Даты опыта хранятся как SQL DATE, текущая работа имеет endDate = null.

[Начальная миграция](prisma/migrations/20261021153000_initial_profile/migration.sql) содержит внешние ключи, каскадное удаление дочерних записей, уникальные индексы и SQL CHECK для периода работы и неотрицательных позиций. CHECK-ограничения поддерживаются SQL-миграцией, поскольку Prisma DSL их не описывает. После создания новых миграций проверяй сохранность этих ограничений.

`npm run db:migrate` позволяет отдельно применить готовую историю без сброса базы. Обычно это выполняется автоматически при старте. Для разработки новых миграций используй `npm run db:migrate:dev -- --name change_name` с отдельной `SHADOW_DATABASE_URL`. Команды db push и migrate reset не являются способом запуска приложения. При непустой неизвестной схеме или неуспешной миграции приложение завершает запуск без сброса данных.

Подготовкой управляет [ресурс БД](src/database/create-prepared-database.ts) в lifecycle NestJS. Seed и API используют один PrismaClient и пул. [Запуск миграций](src/database/deploy-migrations.ts) использует установленную Prisma CLI через Node.js с абсолютными путями; URL передаётся через окружение, shell-интерполяция не используется. Пути конфигурации и миграций не зависят от текущей рабочей папки процесса.

Prisma CLI входит в production-зависимости, поскольку нужна при старте. После предварительной сборки можно запускать `node dist/main.js`; вместе с dist нужны node_modules, prisma.config.ts и каталог prisma со схемой и миграциями. Сборка сама не применяет миграции и не подключается к базе.

## Демонстрационные данные

При старте приложения seed вызывается явно после успешного migrate deploy; автоматическое поведение Prisma Migrate для этого не используется. Для отдельного заполнения служит `npm run db:seed`: npm prehook собирает приложение, затем стандартная команда `prisma db seed` запускает отдельный Node-процесс. Для прямого `npx prisma db seed` сначала выполни `npm run build`. При отдельном запуске seed миграции должны быть применены заранее. Пул закрывается при успехе и ошибке; ошибка завершает процесс с ненулевым кодом.

[Seed](src/database/seed-demo-profile.ts) управляет только профилем с зарезервированным slug `demo-profile`. Поля, коллекции и их порядок берутся из [типизированных данных](src/profile/profile-seed-data.ts). Изменяй этот файл и повторяй команду: существующие дочерние записи обновляются по стабильному key с сохранением id, новые добавляются, удалённые из входного списка записи удаляются только у демопрофиля. Пустой список очищает соответствующий раздел. Другие профили сохраняются, в том числе при совпадении дочерних ключей. Ручные изменения внутри управляемого демопрофиля будут перезаписаны.

До транзакции проверяются непустые обязательные поля, абсолютные HTTP(S) ссылки без учётных данных, календарные даты и порядок периода работы. Ключи должны быть уникальными внутри раздела и состоять из строчных латинских букв, цифр и одиночных дефисов. Даты SQL DATE записываются через UTC без сдвига календарного дня. Валидация календаря общая для seed и GraphQL-скаляра.

Профиль и все коллекции синхронизируются в одной транзакции. Интеграционные тесты вызывают настоящую ошибку ограничения PostgreSQL в последнем разделе и проверяют полный откат как первого заполнения, так и обновления существующих данных. Отдельные тесты запускают сконфигурированную Prisma CLI, проверяя повторный запуск и код завершения при ошибке записи.

Dev-зависимости ts-morph и @apollo/gateway нужны для проверки деклараций пакетов NestJS при skipLibCheck: false. Они не включают федерацию или генерацию SDL из классов в приложении.

В .npmrc включена обычная проверка peerDependencies: legacy-peer-deps=false. Глобальная настройка npm не должна позволять создавать lockfile с несовместимыми peer-зависимостями.

## Типы GraphQL

Настройки находятся в [codegen.ts](codegen.ts). Источник типов — SDL; результат записывается в src/generated/graphql.ts, исключён из Git и не редактируется вручную. `npm run codegen` обновляет GraphQL и Prisma, `npm run codegen:graphql` — только типы GraphQL. Prisma Client генерируется отдельно в src/generated/prisma и также не хранится в Git.

Типы данных и списки неизменяемы. Nullable-поля представлены через null; свойства данных не получают дополнительный undefined. Date явно сопоставлен со string на входе и выходе; [обработчик скаляра](src/graphql/date.scalar.ts) проверяет тип, формат и календарную дату при вводе переменных, литералов и сериализации результата. Новый скаляр без явного сопоставления останавливает генерацию.

Типы функций резолверов включают parent, args, context, info и результат. Сейчас поля схемы не принимают аргументов, поэтому args — Record<PropertyKey, never>. [Контекст запроса](src/graphql/graphql-context.ts) содержит конкретные типы сервиса и загрузчиков. Mapper Profile сопоставляет родителя резолверов с ProfileRecord: он содержит id и основные поля, поэтому корневой резолвер не обязан заранее читать вложенные коллекции. Публичный тип Profile и SDL сохраняют все обязательные поля; id и технические поля БД в API не добавляются.

Команда npm test запускает обычные тесты и отдельные проверки типов через TypeScript. Они проверяют даты, nullability, неизменяемость данных и сигнатуры резолверов. npm run test:watch обновляет типы при старте; после изменения SDL перезапусти эту команду.

## Правила разработки

TDD, функциональный стиль без собственных классов, содержательный JSDoc у каждой функции, строгий TypeScript без any. Эти правила распространяются на тесты и проверяются ESLint. Отрицательные тесты отдельно подтверждают запрет классов, any и функций без JSDoc.
